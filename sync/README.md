# 可选 Supabase 账号同步

本地记餐、收藏、周报、禁忌、购物清单及 JSON 导入导出无需账号。此目录提供可选云端配置，不代表已开通公共同步服务。部署者应使用自己的 Supabase 项目，并决定所在地、计费、访问和备份政策。

## 配置

1. 在 Supabase 创建 PostgreSQL 项目。在 SQL Editor 执行 [schema.sql](schema.sql)。脚本可重复执行，不删除已有备份；每账号保存最新的一份快照。
2. Auth 启用 Email / Password 登录及邮箱确认，配置实际网页的 Site URL 和允许的回调地址、邮件投递。收件人完成邮箱验证后回到网页登录。上线前核对 Supabase 邮件及认证限流。
3. 从项目设置复制 `https://<project-ref>.supabase.co` 地址及 **publishable key**（`sb_publishable_…`）或旧版 **anon JWT key**。网页拒绝 secret / service_role key，这些后台高权限密钥不能放进网页、备份或聊天。
4. 在应用右上角“备份与同步 → 可选账号同步”填写上述公开配置，用邮箱与至少 8 位密码注册。根据项目策略完成邮箱验证后登录。需要浏览器可访问该 HTTPS Supabase 域名。
5. 点击“检查云端版本”。已有云端数据时建议先“下载并预览”，检查 ID 冲突处理与是否恢复目标/禁忌，确认合并后再上传。首次上传或每次上传均需明确确认。
6. 在另一设备打开同一个网页，填写同一项目配置，登录同一账号，下载并预览、合并恢复。上传仅更新此账号的云端快照，不会自动修改其他设备。

## 数据与冲突

- 快照包含饮食、身体与运动资料、次日偏好、收藏、禁忌和购物清单，最大 2 MiB；不包含照片、背景、识别服务配置、公开 key、密码和登录令牌。云端项目管理者可以访问所托管的备份，这不是端到端加密服务。
- 表 `public.diary_snapshots` 的 RLS 只允许账号读取 `user_id = auth.uid()` 的行。匿名角色无表权限，已登录客户端无直接写表权限。写入通过授权的 `put_diary_snapshot` 函数完成；函数固定空 search_path、明确使用 `auth.uid()` 绑定目标，不接受外部传入用户 ID。
- 每次写入携带先前读到的 revision。首次创建必须为 0；后续只有版本相同时才更新并加 1。并发设备先后更新时，旧版本会得到 `sync_conflict`，应用不会自动重试覆盖。先重新下载、预览合并，再上传。
- 下载只打开导入预览，不自动写入。合并以 ID 为准，同名食物可以是不同记录；默认保留本地冲突项。没有传播删除操作或后台自动同步，其他设备删除的记录不会被静默删掉。云端只保存最新快照，请另外定期导出离线 JSON 备份。
- 所有本地数据导入通过带回滚日志的多存储写入，成功后刷新 UI。另一标签页更新数据时会暂停当前页编辑，刷新以载入新状态。
- 密码仅在登录/注册请求时经 HTTPS 发给选定的 Supabase；不存储。会话令牌保存在当前标签页 sessionStorage，退出后清除，失效时尝试刷新。公开项目配置留在 localStorage。共享设备使用完请退出账号并清理站点数据。

## 验证与限制

`npm test` 覆盖 URL/key 校验、登录/邮箱验证、会话刷新、用户行查询、版本冲突与非法备份拒绝（模拟 HTTP）。浏览器验证覆盖注册、登录、下载预览、合并、显式上传、冲突与退出。数据库脚本已在本地 PostgreSQL（PGlite）执行验证：账号行隔离、禁止匿名读取、禁止直接写表、版本比较及大小限制；正式部署后还应使用两个测试账号核对目标项目的实际 Auth 与 RLS 配置。

仓库没有真实 Supabase 项目配置，本次未执行真实云端账号注册或公网同步。为保持静态应用零第三方运行依赖，直接使用 Supabase Auth / REST HTTPS 接口。不支持自建域名或非 `.supabase.co` 地址。自托管、组织登录、端到端加密、自动增量同步与完整历史版本不在本实现范围。

可重跑的数据库验证脚本：

```sh
npm install --no-save --package-lock=false @electric-sql/pglite
npm run test:sync-schema
```

它在内存数据库创建模拟的 `auth.uid()` 和两个测试账号，执行真实 PostgreSQL SQL 与 RLS；不连接你的 Supabase 项目，不处理真实账号数据。
